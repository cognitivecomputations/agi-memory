> ### What this changes
>
> **P0-1 is withdrawn.** Hexis ships as a desktop application, and the credential is an
> OAuth client for an *installed application*. Google's own documentation states that
> for installed apps the client secret is not treated as confidential, and RFC 8252
> ("OAuth 2.0 for Native Apps") says the same: a native client cannot hold a secret,
> so the security model does not depend on it doing so. Packaging it is the documented
> path, not a leak. **The original audit applied a web-server threat model to a desktop
> client.** Do not re-flag it; see the standing note in `CLAUDE.md` and `AGENTS.md`.
>
> That leaves **one** live P0 outranking `bridge_gaps.md`'s sequencing:
>
> - **P0-4 + `bridge_gaps.md` §11.5** — `execute_code` is unsandboxed, unflagged, and
>   running inside a loop whose approval gate is skipped when no callback exists. The
>   one-hour fail-closed change closes the second half; the first half needs the flag
>   set and a sandbox.
>
> **P0-5 and P0-6 are withdrawn for OSS.** API-key authentication belongs to **Hexis
> Pro**; OSS is a desktop application with no auth layer by design. Both findings
> assumed a server product that OSS is not. They remain valid input for Pro.
>
> **This has a consequence the audit could not have seen, and it is not small.** OSS
> will never gain first-party auth, so **remote access can only ever be secured at the
> network layer** — a tailnet, or a reverse proxy that brings its own authentication.

> "premature," it is permanently out of bounds.

> A pattern also worth naming, because it now has six instances across this audit and
> `bridge_gaps.md`: **a mechanism exists, and nothing enforces it.** Checksums computed

**Date:** 2026-07-29 · **Commit reviewed:** `f921921` · **Scope:** whole repository (~300k LOC)

## Method

Five independent reviewers covered the database layer (`db/`), core Python (`core/`),
services/apps/channels, the Next.js UI, and tests/CI/ops. Findings below carry
`file:line` references. Items marked **[verified]** were reproduced directly against
this working copy or the live `hexis_brain` database, not taken on report alone.

## Verdict

The architecture is sound and worth building on. The verification layer has collapsed,
and as a consequence a meaningful fraction of features considered "done" are silently
non-functional in the shipped product.

The dominant failure mode — found independently by all five reviewers — is **silent
degradation dressed as success**: not crashes, but subsystems that report green while
doing nothing. This directly violates the project's own Experience Bar #8 ("never a
silent `except: pass`"). It is now the default behavior in every part of the system
that has not been driven by hand.

The mechanical root cause: CI has failed 55 of its last 60 runs and has never once been
green, while `publish.yml` has no `needs:` dependency on it. Once the gate stopped
meaning anything, the failures it was correctly reporting began shipping to users.

**None of this is architectural.** No rewrite is implied. Estimated 2–3 weeks of
unglamorous work, and the highest-leverage single change is P0-2 + P0-3 (green CI,
gated publish), which converts most remaining items from "silently shipping" to
"cannot ship."

# P0 — Ship blockers

### P0-1. Live Google OAuth client secret committed and published to PyPI **[verified]**

- **Where:** `core/auth/gmail-credentials.json`; packaged by `pyproject.toml:121-122`;
  loaded at `core/auth/google_gmail.py:43`. Tracked in git since `fe9f2a0`.
- **Detail:** Contains a real `client_secret` (`GOCSPX-…`) for GCP project
  `samantha-466214`. A token-endpoint probe returned `invalid_grant`, **not**
  `invalid_client` — the credential pair was accepted by Google and only the dummy
  refresh token was rejected. The credential is live and public.
- **Impact:** Anyone can consume its quota. A Google-side revocation or verification
  action breaks Gmail auth for every installed user simultaneously. Present in every
  published wheel.
- **Fix:** Rotate/revoke the client in GCP now. Remove from git history
  (`git-filter-repo`), drop the `package-data` entries, and require users to supply
  their own OAuth client — or proxy through a service you control. Note that
  `tests/conftest.py:21-24` already autouses a fixture to stop tests consuming it,
  which suggests the hazard was recognized.
- **Effort:** hours (plus history rewrite coordination).

### P0-2. Releases ship from permanently-red CI **[verified]**

- **Where:** `.github/workflows/publish.yml:6-10` triggers on `push: main` and `tags: v*`
  with no `needs:` on CI and no reference to `all-checks-pass`.
- **Detail:** Last 15 CI runs: 13 failure, 2 cancelled, 0 success. Last 60: 55 failure,
  5 cancelled, 0 success. v1.0.7 was tagged, imaged, and published to PyPI on 2026-07-27
  while both blocking lanes (`test`, `migration-survivor`) were failing.
  `all-checks-pass` (`.github/workflows/ci.yml:178-190`) is written correctly but has
  never returned success, so it gates nothing.
- **Fix:** Make `publish.yml` depend on the CI gate. Confirm `all-checks-pass` is set as
  a required branch protection check and is not being bypassed.
- **Effort:** hours — but blocked on P0-3 for CI to be greenable.

### P0-3. `search_path` misconfiguration ships to users and breaks the upgrade path **[verified]**

- **Where:** `ops/docker-compose.runtime.yml:35` (`search_path=ag_catalog,public`) vs.
  `docker-compose.yml:70` (`search_path=public,ag_catalog`, with a comment citing
  migration `0043`). CI reproduces the broken ordering at `.github/workflows/ci.yml:79,141`.
- **Detail:** Five baseline files omit the `SET search_path = public, ag_catalog, "$user";`
  header that the other 87 carry: `db/27_functions_sessions.sql` (5 functions),
  `db/28_functions_dopamine.sql` (14), `db/31_functions_recmem.sql` (35),
  `db/48_functions_memory_exchange.sql` (26), `db/57_functions_hmx_digest.sql` (14).
  Under an `ag_catalog`-first default, ~94 functions land in the wrong schema.
- **Impact:** This is the cause of most CI failures — the tests are correct and the
  product is wrong. `migration-survivor` fails with
  `function "public.claim_recmem_unembedded_batch(integer, integer)" does not exist`.
  A fresh `pip install hexis && hexis up` reproduces it. `heal_schema_shadows()` cannot
  repair it: these functions have no public twin to fall back to.
  `db/migrations/0043_one_brain_one_schema.sql` claims all three locations were flipped
  in one commit; two of the three were not.
- **Fix:** Add the header to the five files, flip `ops/docker-compose.runtime.yml:35`
  and both CI service definitions, and add a test asserting every `db/*.sql` carries the
  header. Also fix `db/migrations/README.md`, which documents the *wrong* ordering as
  what the runner sets (actual: `core/migrations.py:121`).
- **Effort:** days (fix is small; validating the ~90 downstream test failures is the work).

### P0-4. `execute_code` is unsandboxed RCE with no approval gate in the autonomous loop **[verified]**

- **Where:** `core/tools/code_execution.py:86-88` declares `requires_approval=False` and
  `allowed_contexts={CHAT, HEARTBEAT}`; registered by default at
  `core/tools/registry.py:752`. Backing REPL: `services/rlm_repl.py:89-90` ships
  `"__import__": __import__` and `"open": open` in `_SAFE_BUILTINS`; executes in-process
  via `exec` at `:249`.
- **Detail:** `__import__('os').system(...)` is arbitrary code execution as the worker
  process, with `PGPASSWORD`, provider API keys, and OAuth tokens in `os.environ`. Even
  without `__import__`, restricted-builtins sandboxes are escapable via
  `type`/`object`/`getattr`/`super`, all of which are present.
- **Impact:** Any prompt injection reaching a heartbeat — ingested document, Gmail body,
  fetched web page, MCP tool result — is a direct path to code execution.
- **Fix:** Either set `requires_approval=True` and drop `HEARTBEAT` from
  `allowed_contexts`, or move execution into a real sandbox (subprocess with seccomp,
  container, or gVisor). Remove `__import__`/`open` from `_SAFE_BUILTINS` regardless —
  and stop describing it as "sandboxed" in the tool description until it is.
- **Related:** `core/tools/dynamic.py:370-434` persists agent-authored Python into the
  `config` table and `exec`s it on every startup. Stricter builtins, gated behind
  `tools.allow_dynamic` + approval, but the `object.__subclasses__()` escape still
  applies. `plugins/loader.py:229-247` similarly `exec_module()`s any path named in
  `plugin.external_dirs` config with no signing or allowlist.
- **Effort:** days.

### P0-5. `HEXIS_API_KEY` cannot be enabled in any shipped deployment **[verified]**

- **Where:** Read at `apps/hexis_api.py:111`; middleware installed only when set
  (`:126-127`). Neither `docker-compose.yml:249-266` nor
  `ops/docker-compose.runtime.yml:183-200` passes it, and neither declares `env_file:`.
  The UI proxy reads `process.env.HEXIS_API_KEY` (`hexis-ui/lib/python-api.ts:20`) and
  doesn't receive it either.
- **Impact:** `docs/operations/production.md:68` instructs operators to set it for API
  authentication. Following that doc in the default Docker deployment produces a
  silently unauthenticated API. Zero tests cover the middleware.
- **Consequence — unauthenticated side-effecting endpoints:** `/api/heartbeat/run`
  (`:1345`), `/api/integrations/action` incl. `revoke_gmail_connection` and
  `start_gmail_backfill` (`:989-1119`), `/api/inbox/reply` (`:746`),
  `/api/ingest/{text,url,file}` (`:1541-1717`), `/api/webhook/{source}` (`:1300`).
  The file-upload endpoint is `multipart/form-data` (CORS-preflight-exempt) and the
  webhook accepts any body (`:1307-1310`) — so any page the user visits can write into
  the agent's memory and trigger LLM spend on `127.0.0.1:43817`. Loopback binding does
  not protect against this or against DNS rebinding.
- **Fix:** Pass the variable through both compose files; add a startup warning when
  unset; add middleware tests. Consider CSRF tokens or an `Origin` check on the Next
  layer, which has no auth at all across its 60 route handlers and holds the
  `postgres://` credentials directly.
- **Effort:** days.

### P0-6. Bearer auth forwarded by only half the UI proxy routes

- **Where:** `hexis-ui/lib/python-api.ts:18-25` attaches the key; ~10 routes use it,
  ~10 do not — including `/api/chat` (`hexis-ui/app/api/chat/route.ts:29-36`),
  `/api/events/stream`, all five `/api/ingest/*`, `/api/init/consent/*`, `/api/init/models`.
- **Impact:** Because `apps/hexis_api.py:113-126` applies the middleware to every path
  except `/health` and the Gmail callback, *setting* `HEXIS_API_KEY` breaks chat, ingest,
  and the event stream from the web UI while other pages keep working — a silent,
  confusing half-failure. This is why P0-5 cannot simply be "turn it on."
- **Fix:** Route every proxy handler through `hexisApiHeaders()`. Add a test asserting
  no route file calls bare `fetch(resolveHexisApiUrl(...))`.
- **Effort:** hours.

### P0-7. Migration checksums recorded but never verified **[verified: 9 already drifted]**

- **Where:** `core/migrations.py:153` computes SHA-256 and stores it (`:161`, `:170`);
  skip logic at `:147-151` is `if version in done: continue`. The checksum is never compared.
- **Detail:** On the live DB, 9 of 196 applied migrations have on-disk content differing
  from their recorded checksum. `0103_integration_connectors.sql` applied 2026-07-23,
  then was rewritten in `fe9f2a0` on 07-24 (+26/-9 lines), materially changing the Gmail
  OAuth connector manifest — that edit will never apply to any database that ran 0103 first.
- **Impact:** Two databases built from the same commit can have different schemas, with
  no detection.
- **Fix:** Compare and fail loudly (~10 lines). Provide an explicit override for
  intentional edits.
- **Effort:** hours.

# P1 — Silently broken features

### P1-1. Plugins and dynamic tools are invisible to the agent's own runtimes **[verified]**

- **Where:** `create_full_registry` (`core/tools/registry.py:803-846`) is the only factory
  that loads plugins, persisted dynamic tools, and plugin skill dirs. Its **only**
  non-test caller is `apps/hexis_mcp_server.py:734`. The worker
  (`services/worker_service.py:1254`), API (`apps/hexis_api.py:1073,1109,1181,1411`),
  chat (`services/chat.py:292,456,599`), CLI, and TUI all use `create_default_registry`.
- **Impact:** All seven bundled plugins (todoist, asana, hubspot, youtube, twitter,
  fathom, video_gen) and every agent-authored dynamic tool are unavailable to heartbeat
  and chat. No test asserts plugin availability in a runtime path.
- **Fix:** Make the runtimes use the full registry (it is async — check startup ordering),
  and add a test asserting a known plugin tool is reachable from the worker's registry.
- **Effort:** days.

### P1-2. Heartbeat can wedge permanently while status reads green

- **Where:** `services/worker_service.py:428-453` — `start_heartbeat()` sets
  `active_heartbeat_id` before the gateway submit; if the submit fails the code logs and
  returns **without releasing**. `should_run_heartbeat()` then returns FALSE forever
  (`db/07_functions_heartbeat.sql:941-943`). No stale-claim reaper exists —
  `recover_interrupted_worker_runs` (`db/88_functions_worker_runtime.sql:365-408`) touches
  only worker rows.
- **Also:** the manual endpoint's release sits inside `except Exception`
  (`apps/hexis_api.py:1447-1450`), so a client disconnect (`GeneratorExit`/`CancelledError`)
  leaks the claim.
- **Impact:** The autonomy loop — the product thesis — stops permanently, and
  `hexis status` shows a benign "idle" (`apps/hexis_cli.py:3286-3291`).
- **Fix:** Release in `finally`, catch `BaseException`, and add a stale-claim reaper with
  a heartbeat-age threshold.
- **Effort:** days.

### P1-3. `is_group` is always `False` on the multi-user platforms

- **Where:** `channels/base.py:58-67` reads only `metadata["is_group"]`/`["is_private"]`.
  Discord sets `is_dm` (`discord_adapter.py:193-195`), Slack sets `channel_type`
  (`slack_adapter.py:194-196`), Matrix sets `room_name`/`room_member_count`
  (`matrix_adapter.py:175-178`).
- **Impact:** Drives `exclude_sensitive` at the recall layer (`services/agent.py:736`).
  A privacy control that keeps private memories out of shared rooms reports the safe
  answer while doing nothing.
- **Fix:** Normalize per-adapter into the key `base.py` reads; add a test per adapter.
- **Effort:** hours.

### P1-4. Streaming replies silently drop long messages on 4 of 7 channels

- **Where:** `channels/manager.py:325` routes every edit-capable adapter (Discord,
  Telegram, Slack, Matrix) to `StreamCoalescer`, which sends `self._total_text`
  **unchunked** (`channels/streaming.py:100-136`). `chunk_text`/`max_message_length` is
  applied only on the non-streaming path (`manager.py:329-334`).
- **Impact:** Over Discord's 2000-char limit the send raises, is caught, returns `None`;
  `flush()` retries the whole thing and fails again; edit failures are swallowed by
  `except Exception: pass` (`streaming.py:137-138`). Worse,
  `channels/conversation.py:298-318` accepts `message_id = None` and still writes the
  assistant turn — **the DB records a delivery that never happened.**
- **Fix:** Apply chunking in the streaming path; treat `message_id is None` as a failure.
- **Effort:** days.

### P1-5. Token/cost accounting records zero for every streaming call **[verified]**

- **Where:** All seven streaming paths return `"raw": None` — `core/llm.py:428, 1132,
  1418, 1502, 1604`, `core/providers/anthropic_http.py:286`,
  `core/providers/google_code_assist.py:376`. `record_llm_usage` extracts from `raw`
  (`core/usage.py:155`) and `extract_usage(None)` returns all zeros (`core/usage.py:39-40`).
- **Impact:** Chat is streaming, so `api_usage` and every cost/budget/quota feature built
  on it is wrong by ~100% for the primary workload — and fails silently.
- **Fix:** Capture usage from the final streaming chunk per provider
  (`stream_options.include_usage` for OpenAI-compatible, `message_delta` for Anthropic).
- **Effort:** days.

### P1-6. Silent-failure sites that mask real breakage

- **DB:** 202 `EXCEPTION WHEN OTHERS THEN NULL` handlers (of 443 `WHEN OTHERS` total).
  Confirmed concrete impact: `find_episode_memories_graph` ends with
  `EXCEPTION WHEN OTHERS THEN RETURN;` (`db/02_functions_deliberate_transformation.sql:1117-1118`).
  AGE is in neither `shared_preload_libraries` nor `session_preload_libraries`, so any
  connection that hasn't run `LOAD 'age'` gets **0 rows instead of an error** — verified:
  same episode returns 0 without the load and 1 with it, while the graph holds 3,329
  `IN_EPISODE` edges. This zeroes the episode-binding term of the ranker
  (`db/31_functions_recmem.sql:1840-1849`) and, via `assign_to_episode`
  (`db/04_functions_core.sql:62-71`), makes the 30-minute episode-gap rule unreachable —
  episodes never close and `sequence_order` stays 1. `core/cognitive_memory_api.py:196`
  does issue `LOAD 'age'`, so the main path is covered; the blast radius elsewhere is severe.
- **Python:** ~48 silent `except: pass` in `core/`. Worst:
  `core/cognitive_memory_api.py:194-204` (swallows `SET search_path` failure — causes
  confusing "function does not exist" errors far from the cause);
  `core/tools/memory.py:48-49` (recall hot path, discards exception without logging);
  `core/agent_api.py:36-48` (falls through to env defaults — the exact "silently reuse
  ambient state" case Experience Bar #5 forbids).
- **Subconscious:** `services/subconscious.py:97-113` converts errors into
  `{"skipped": True}`, `_result_has_work` treats that as no-work
  (`worker_service.py:72-83`), and `mark_subconscious_decider_run` fires regardless
  (`:932-933`). A permanently broken subconscious is invisible to `status` and `doctor`.
- **Fix:** Log every swallowed exception with context. Reserve bare returns for paths
  that are genuinely advisory, and make those observable.
- **Effort:** days (mechanical but broad).

### P1-7. Prompt source-of-truth is split and has already drifted

- **Where:** `conscious_extraction` is read from the DB (`services/extraction.py:56-58`),
  so on any existing database it runs migration `0084`'s 5,358-char text while the disk
  file is 6,362 chars. Editing the `.md` has zero runtime effect;
  `db/40_seed_prompt_modules.sql` executes only on a fresh volume. 8 of 13 `.md`-backed
  DB keys are stale vs. disk. `scripts/gen_prompt_seed.py:7` is honor-system with no CI
  regeneration check. Golden tests compare DB↔fixture, never disk↔DB
  (`tests/db/test_prompt_render.py:206-212`).
- **Related:** `compose_personhood` (`db/39_functions_prompt_render.sql:1010`) has no
  production caller. What reaches the model is `_COMPACT_PERSONHOOD`, ~1,900 chars of
  untested prose in a Python dict (`services/prompt_resources.py:257-322`, injected at
  `services/agent.py:633`) containing substantive policy that exists nowhere in
  `personhood.md`. The module docstring at `:339-343` asserts the opposite.
- **Fix:** Pick one source of truth. Add a CI check that regenerates the seed and fails
  on drift.
- **Effort:** days.

### P1-8. Baseline and migrations have measurably diverged

- **Detail:** Of 745 function definitions parsed from `db/*.sql` and compared against the
  live DB, **18 differ**. `file_resource_request` is semantically different: the
  committed baseline (`db/74_functions_resource_requests.sql`) has input validation,
  `RAISE EXCEPTION` handling, and `web_inbox` delivery with a machine-readable
  `request_id`; the live DB runs an older body returning
  `jsonb_build_object('error', ...)` with no inbox integration.
- **Cause:** an ordering trap — on a *fresh* DB the baseline applies first and the
  migration overwrites it; on an *existing* DB only the migration ever ran. Editing
  `db/*.sql` alone is a no-op on existing databases *and* is reverted on new ones.
  `db/migrations/README.md:35-37` claims "the two never diverge in effect"; nothing
  enforces it.
- **Fix:** Add a CI check diffing baseline-derived function bodies against
  baseline+migrations. Treat divergence as a failure.
- **Effort:** days.

### P1-9. Message loss and lost-update races

- **Inbox loss by design:** `core/rabbitmq_bridge.py:141-181` uses
  `ackmode: "ack_requeue_false"` — acking messages off the broker *before* writing them
  to working memory. A DB hiccup drops user-to-agent messages permanently on a logged
  warning. For a product whose pitch is continuity, this is a values-level bug.
- **Outbox non-durable:** `rabbitmq_bridge.py:75-84` publishes without `delivery_mode: 2`
  on a durable queue, so outbox messages vanish on broker restart. (The new inbox
  publisher at `:105-117` *does* set it — so this is an oversight, not policy.)
  `publish_outbox_payloads` also `return`s on first failure mid-batch (`:89-91`),
  silently dropping the remainder.
- **`heartbeat_state` lost updates:** it is a VIEW over one JSONB blob
  (`db/90_views.sql:57-77`) whose `INSTEAD OF` trigger rebuilds all 15 fields and
  overwrites wholesale (`db/07_functions_heartbeat.sql:684-709`). Every
  `UPDATE heartbeat_state SET one_column = …` is a read-modify-write of the whole
  document with no row lock and no version column — 16 such sites across 8 files plus
  `core/capability_maturity.py:200`. The heartbeat worker, chat path, and admin path
  clobber each other under concurrency.
- **Heartbeat admission TOCTOU:** `should_run_heartbeat()` reads `active_heartbeat_id`

### P1-10. Chat SSE loses the turn on client disconnect

# P2 — Performance and scale

### P2-1. The primary HNSW vector index has never been used **[verified: `idx_scan = 0` lifetime]**

- **Where:** `idx_memories_embedding` is partial on `embedding_status = 'embedded'`
  (`db/01_indices.sql:7-8`), but the seed scans in `recmem_recall_context` filter only on
  `status`, `type`, `valid_until`, and `embedding IS NOT NULL`
  (`db/31_functions_recmem.sql:1797-1830`) — the planner cannot prove the index predicate.
  Adding `embedding_status='embedded'` flips the plan to `Index Scan`; the additional
  `m.embedding <> zero_vec` filter flips it back to a sort. Same defect kills
  `idx_subconscious_unit_chunks_embedding` (also `idx_scan = 0`).
- **Impact:** `fast_recall` — the flagship path — is a sequential scan wearing a
  vector-search costume. At 3,330 rows it costs ~2ms and is invisible. The entire design
  premise is that this scales.
- **Fix:** Align the query predicates with the index predicate, or drop the partial clause.
  Add a regression test asserting the plan uses the index at a seeded row count.
- **Effort:** days.

### P2-2. Unbounded scans in the subconscious recall tier

- `chunk_best` and `parent_hits` in `recmem_subconscious_vector_hits` have no `LIMIT`
  (`db/31_functions_recmem.sql:1561-1627`) — every recall computes cosine distance against
  *every* active embedded unit and *every* chunk, plus a correlated `COUNT(*)` per unit via
  `CROSS JOIN LATERAL` (`:1595-1599`), before the outer `LIMIT` applies. Fine at 114 units;
  quadratic-feeling at 100k conversation turns.

### P2-3. Per-token database write on the streaming hot path

- `core/agent_loop.py:397-402` → `_emit` (`:985-995`) acquires a pool connection and runs
  `record_agent_turn_event` **per event**, awaited *before* forwarding the token. A
  1,000-token reply is 1,000 pool acquisitions and 1,000 INSERTs.
- **Fix:** Batch events, or write asynchronously off the critical path.

### P2-4. Full tool-catalog round-trip on every tool execution

- `core/tools/registry.py:279` calls `sync_tool_catalog()` before every
  `evaluate_tool_call`, serializing all ~152 specs (`:156-181`) and writing them.
  `get_specs` (`:234`), `get_mcp_tools` (`:254`), and `get_enabled_tools` (`:215`) each do
  it again. One turn with 5 tool calls performs ~7 full-catalog serializations and writes.

### P2-5. `fast_recall` is declared `STABLE` but writes and performs network I/O

- `db/04_functions_core.sql:130` marks it `STABLE`; it transitively calls `get_embedding`,
  which does `INSERT INTO embedding_cache` (`db/03_functions_helpers.sql:346`),
  `INSERT INTO api_usage` (`:355`), and blocking `http_post`. `get_embedding` also retries
  in a loop with `pg_sleep` for up to 30s (`:302-306`), holding a transaction and its
  snapshot open. This lies to the planner and breaks in read-only transactions.

### P2-6. No prompt caching; ~6.4–7k tokens re-billed per chat turn

- No `cache_control`/`ephemeral` anywhere in the repo. `conversation.md` alone is 5,858
  tokens and is `read_text()`-ed synchronously on **every** turn
  (`services/prompt_resources.py:235`, uncached — unlike 10 sibling loaders that are
  `lru_cache`d). Opt-in addenda add +10,161 tokens (`philosophy.md`, 51% of which is
  ASCII box-drawing) and +2,414.

### P2-7. Maintenance loop is strictly sequential head-of-line blocking

- All 19 tasks run in order per tick (`services/worker_service.py:1135-1136`) and
  ingestion jobs process inline (`services/ingest/jobs.py:163-170`). A large PDF ingest
  stalls outbox delivery, scheduled tasks, and embedding for its whole duration — and
  `_mark_worker_seen` (`:1128`) isn't called meanwhile, so the worker also *looks* stale.

### P2-8. N+1 in the summarization path

- `apply_memory_summary` calls `get_embedding` once per lesson inside a `FOR` loop
  (`db/47_functions_retention.sql:~278`) — one HTTP round-trip each, despite
  `get_embedding` accepting an array — each followed by an unindexable ANN dedup scan.

### P2-9. Per-module test setup cost

- `temp_test_db` is `autouse=True` (`tests/conftest.py:40`), so all 237 modules pay
  `CREATE DATABASE` + replay of 96 baseline files (~47k lines) + 196 migrations (~48k
  lines) — including modules that touch no database. ~11 minutes for the pytest step.

# What is genuinely strong

Recorded so the list above is read in proportion. These are things most codebases at this
stage do not have:

- **The DB-as-brain thesis is really implemented.** `core/agent_loop.py:466-517` asks
  Postgres what to do next, applies results back (`:818-844`), re-reads the authoritative
  message log rather than keeping a parallel Python list, and reads energy totals from the
  DB (`:603`). Turn state survives process death. This is the hardest part of the thesis
  and it is done.
- **Injection surface is clean** despite ~55 dynamic-Cypher sites — values go through
  `%L`/`quote_literal`, identifier positions are enum-typed or `CASE`-whitelisted. All 21
  UI `$queryRawUnsafe` sites bind parameters.
- **Worker concurrency is correct where it counts** — 26 `FOR UPDATE SKIP LOCKED` sites,
  correct claim/backoff/max-attempts in every queue function, `pg_advisory_xact_lock`
  around `assign_to_episode`'s read-modify-write.
- **Delivery obligations are honest at-least-once** (`channels/outbox.py:429-637`) —
  recorded before send, claimed, recovered on restart, with recovered messages explicitly
  marked as possible duplicates. Better than many production systems.
- **The schema-shadow guard** (`db/64_functions_schema_guard.sql`) and the
  `migration-survivor` CI lane (`ops/ci/migration_survivor.py:57-131`) are what careful
  people build after getting burned. The survivor lane is failing because it is working.
- **The test corpus is real** — 2,643 tests, 237 modules, 172 hitting an actual Postgres
  with a per-module throwaway database replaying baseline + all 196 migrations. Only 7
  skips. Not mock theater.
- **`core/integration_reliability.py`** is a genuinely good shared HTTP substrate: RFC 9110
  `Retry-After` including HTTP-date form, jittered backoff with injectable `random_fn`,
  bounded error bodies, correlation IDs, injectable transport.
- **Maintenance loop supervision** — 19 named tasks each wrapped by `_run_observed_task`
  (`services/worker_service.py:724-756`) recording per-task outcomes; one broken task
  cannot kill the loop.
- **Skill catalog is tri-state with next steps** (`skills/base.py:191-264`) — "can you do
  X?" cannot dead-end in a bare no. The Experience Bar implemented in code.
- **Defaults derived from live truth** — model list and default from models.dev with disk
  cache and free-text escape (`apps/tui/model_catalog.py:19-56`); `hexis_init.py:36-38`
  explicitly refuses to hardcode.
- **Terminal medium respected** — `unsafe_ask_async` so Ctrl+C works, builtin `input()`
  where readline matters, `hexis ui` waits for the port before opening a browser, `lsof`
  names the process holding a busy port.
- **Errors say what/why/next** — difflib suggestions for unknown tools, "run `hexis
  migrate`" on missing DB functions, one-line DB-down messages instead of tracebacks.
- **No XSS in the UI** despite rendering LLM markdown — `escapeHtml` runs before the
  formatting regexes, with an `<img src=x onerror=…>` regression test.
- **Release tagging is well-designed** — correct `edge`/`sha-*`/semver/`latest` model,
  multi-arch, PyPI trusted publishing via OIDC, and a guard refusing to publish on
  tag/version mismatch (`publish.yml:97-104`).
- **Comments explain *why*, with issue references** — unusually good for a codebase this young.
